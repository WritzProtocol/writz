# Production Trusted Setup Ceremony

The keys currently in
`circuits/keys/` were generated by `circuits/scripts/setup_dev.sh` with
scripted, non-random entropy — anyone who ran (or observed) that script knows
the "toxic waste" and can forge arbitrary valid proofs. Before mainnet, every
circuit's proving/verification keys must come from a real multi-party
ceremony.

## Scope: all 4 circuits

`deposit`, `borrow_repay`, `liquidation`, and `zero_debt`. `zero_debt`'s
verification key gates the cooperative Path A release endpoint
(`/api/cosign`); a forged zero-debt proof lets an attacker drain a UTXO with
no BTC ever having been repaid — the same severity class as the other three.
All four circuits go through this same ceremony process.

## Requirements (from `docs/scf/milestone-plan.md` and `docs/research/circom-circuit-design.md`)

- **Minimum 5 independent participants** per circuit.
- **Publicly verifiable transcript** — every contribution's hash is recorded
  and published before the next participant contributes.
- **No participant may contribute without providing their own real entropy.**
  Never pass `-e` with a scripted/predictable value.

## Roles

- **Coordinator**: runs `00_fetch_ptau.sh` and `01_new_zkey.sh` once per
  circuit, distributes the zkey to participants in sequence, and runs
  `03_verify_transcript.sh` + `04_export.js` at the end.
- **Participants** (≥5 per circuit, independent — not all Writz team members):
  each runs `02_contribute.sh` once per circuit, in turn.

## Step by step

```bash
cd circuits

# 1. Coordinator: fetch and checksum-verify the Hermez Powers of Tau file.
#    See 00_fetch_ptau.sh's own comments — you MUST pin a real, independently
#    verified checksum in ceremony/PTAU_CHECKSUM.txt before this will run.
bash scripts/ceremony/00_fetch_ptau.sh 15

# 2. Coordinator: compile circuits if not already done.
bash scripts/compile_all.sh

# 3. Coordinator: start each circuit's ceremony (produces 0000.zkey + transcript.json).
for circuit in deposit borrow_repay liquidation zero_debt; do
  bash scripts/ceremony/01_new_zkey.sh "$circuit"
done

# 4. Each participant, in turn, for EACH circuit:
#    - Receive the previous zkey (out-of-band: a secure file transfer, not email).
#    - Verify its published SHA-256 matches what the previous participant announced.
#    - Run 02_contribute.sh interactively (do not automate — it prompts for entropy).
bash scripts/ceremony/02_contribute.sh deposit "<your name>" \
  ceremony/deposit/0000.zkey ceremony/deposit/0001.zkey
#    - Publish the output SHA-256 publicly before handing off to the next participant.

# 5. After the last participant, coordinator verifies each circuit:
for circuit in deposit borrow_repay liquidation zero_debt; do
  bash scripts/ceremony/03_verify_transcript.sh "$circuit"
done

# 6. Coordinator exports each circuit's final verification key + contract shape:
for circuit in deposit borrow_repay liquidation zero_debt; do
  node scripts/ceremony/04_export.js "$circuit" ceremony/"$circuit"/<final>.zkey
done
```

`04_export.js` prints the remaining manual steps (publishing the `.zkey` as a
GitHub Release asset, copying artifacts into `frontend/`, and running the
on-chain rotation) — follow them in order.

## Verifying someone else's contribution before adding your own

Before running `02_contribute.sh`, always:

1. Confirm the input zkey's SHA-256 matches what the previous participant
   published (the script prompts you to confirm this).
2. Optionally, run `snarkjs zkey verify` yourself against the r1cs and ptau
   before contributing — this replays the entire chain up to that point and
   would catch a corrupted or tampered intermediate zkey.

## What's committed to git vs. published elsewhere

- **Committed**: `circuits/keys/*_vkey.json` (verification keys — small,
  public by design), `circuits/ceremony/*/transcript.json` (the audit trail),
  `circuits/ceremony/*/vkey.contract.json`, `circuits/keys/CEREMONY_MANIFEST.json`.
- **Not committed** (see `circuits/.gitignore`): `circuits/ceremony/*/*.zkey`
  (large binaries — proving keys). Publish these as GitHub Release assets
  instead; the manifest records their hash and release URL so anyone can
  independently fetch and re-verify them.

## Key rotation runbook (after a ceremony completes)

Distinguish **recompiling** a circuit (only needed if `.circom` source logic
changes — regenerates `.wasm` too) from **rotating ceremony keys** (only
`.zkey`/`vkey.json` change — this is what a ceremony run produces). Phase 2
of a ceremony only re-randomizes toxic waste; it never touches the
constraint system, so witness generators (`.wasm`) never need to change as
part of a rotation.

1. Bundle 3–4 `set_verification_key` calls (one per rotated circuit) against
   the `zk-verifier` Soroban contract into a **single Stellar transaction** —
   Soroban supports multiple `InvokeHostFunction` operations per transaction,
   so this is atomic at ledger-close granularity.
2. In the same deploy window, swap `frontend/public/circuits/<circuit>_final.zkey`
   for each rotated circuit, and — if `zero_debt` was rotated —
   `frontend/src/circuits/zero_debt_vkey.json` (this one is bundled into the
   Next.js build, not fetched at runtime; requires a frontend redeploy, not
   just a static asset swap).
3. There is no legitimate reason to roll back to the old (dev) keys after a
   real ceremony. If a rotated key is later found defective: pause new proof
   submission at the application layer, fix the issue, and run a **new**
   ceremony through this same process — never silently fall back.

## CI gate

Any PR touching `circuits/keys/**` triggers the `circuits-ceremony-verify`
job (`.github/workflows/ci.yml`) — it re-runs `snarkjs zkey verify`,
checks the manifest's recorded hashes against the committed files, and
rejects any transcript with a "dev"-named participant. This is a mechanical
sanity check, not a substitute for the human verification steps above.
