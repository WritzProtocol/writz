# Writz Protocol — BUIDL Details

## What is Writz?

Writz is a non-custodial Bitcoin lending protocol built on Stellar. It lets Bitcoin holders borrow native USDC without selling their BTC, without trusting a custodian, and without exposing their position on-chain — using zero-knowledge proofs for full financial privacy.

The core problem: Across Latin America, millions of people save in Bitcoin to escape local currency inflation. But when they need cash — for rent, medical bills, or business opportunities — they face a painful choice: sell their BTC (losing long-term upside and triggering taxes) or go without. Traditional DeFi lending requires handing your Bitcoin to a bridge custodian (centralized risk) and makes your position publicly visible (front-running, liquidation bot sniping).

Writz solves both problems at the protocol level.

## How It Works

Writz operates across two blockchains simultaneously — Bitcoin for collateral custody, Stellar/Soroban for lending logic:

### 1. Deposit (Bitcoin Side)

The user sends BTC to a P2WSH (Pay-to-Witness-Script-Hash) address generated by a Bitcoin Script with two spending paths:

- Path A (Cooperative Release): Both the user and the Writz protocol co-sign a PSBT to release the BTC after loan repayment.
- Path B (Emergency Exit): After a CLTV timelock expires, the user can unilaterally reclaim their BTC — even if Writz disappears entirely.

This means the BTC never leaves the Bitcoin network and is never held by any company, multisig federation, or bridge.

### 2. Verify (Relayer to Soroban)

A TypeScript relayer service watches the Bitcoin blockchain and constructs an SPV (Simplified Payment Verification) proof bundle — block headers, Merkle inclusion proof, and the raw transaction. This bundle is submitted to the bitcoin-spv Soroban contract, which cryptographically verifies the Bitcoin deposit happened without trusting any oracle or third party.

### 3. Commit (ZK Privacy Layer)

The deposit amount is hidden inside a Poseidon hash commitment and inserted into an on-chain Merkle tree (commitment-tree contract). From this point forward, the user's position — deposit amount, loan size, health ratio — is invisible to everyone except the user.

### 4. Borrow (Soroban Smart Contracts)

The user generates a Groth16 zero-knowledge proof (BN254 curve) proving:

- Their collateral exceeds 150% of the requested loan amount
- The commitment exists in the Merkle tree
- The nullifier has not been used before (prevents double-borrowing)

The zk-verifier contract validates the proof using Stellar's Protocol X-Ray host functions (bn254.pairing_check). If valid, the commitment-tree contract releases native Circle USDC from the lending pool to the borrower's Stellar wallet.

### 5. Repay and Release

The user repays USDC plus interest. A new ZK proof verifies the repayment. The protocol co-signs the Bitcoin PSBT (Path A), and the user broadcasts it on Bitcoin to reclaim their BTC.

## Technical Architecture

### Smart Contracts (Rust/Soroban — all deployed on Testnet)

- bitcoin-spv: Verifies Bitcoin transactions on Soroban via SPV proof validation (block headers, Merkle proofs, SHA256d). Contract ID: CAE5L7BO2GNF7MIZWXB2BTUMLYNIMQZUSWN2BWLZQS7HRHLOUSL6VLWJ

- zk-verifier: Validates Groth16 BN254 zero-knowledge proofs using Stellar's Protocol X-Ray host functions. Contract ID: CDV45GLXG4AOU6BDZSY5YHHVNGQIAYAPD3PUGXIIIYLIO6V2XGO6SMFV

- commitment-tree: Poseidon Merkle tree (depth 20) storing encrypted position commitments plus lending pool logic (deposit, borrow, repay). Contract ID: CC2OZ3LG5U6RE3U7QC2R5QMID5GHQBE7QXTJQ4ZSTP5W73WDTKQPRW7E

- private-lend: Non-ZK PrivateLend skeleton for future expansion. Contract ID: CCLH2GJYG3QSHZJI7V7VK3DNMNK3I3QJCECBSFGX3AC6CK4I7EF7ZJ2G

### ZK Circuits (Circom + snarkjs)

- deposit.circom: Proves a valid Poseidon commitment was computed from (amount, secret, nullifier)
- borrow_repay.circom: Proves collateral ratio is at least 150% and Merkle membership without revealing amounts
- liquidation.circom: Proves a position is undercollateralized (below 120%) to trigger liquidation

### Relayer Service (TypeScript/Bun)

- Watches Bitcoin (Signet) via Esplora API for deposit confirmations
- Constructs and serves SPV proof bundles (block headers plus Merkle inclusion proofs)
- Maintains a local Merkle tree leaf store (SQLite) synchronized with on-chain state
- Stores encrypted recovery notes for cross-device position restoration
- Live at: https://writz-relayer-production.up.railway.app

### Bitcoin Script Toolkit (TypeScript)

- Generates P2WSH locking scripts with cooperative (Path A) and timelock (Path B) spending paths
- Handles PSBT construction, multi-party signing, and witness assembly
- Verified end-to-end on Bitcoin Signet with real broadcast transactions

### Frontend (React + Vite)

- Stellar wallet integration via Stellar Wallets Kit (Freighter, LOBSTR, xBull)
- Bitcoin wallet integration via Xverse/sats-connect
- In-browser ZK proof generation using snarkjs
- Live at: https://writz-protocol.vercel.app

## Stellar Integration Depth

Writz is not a superficial Stellar integration — it uses Stellar as load-bearing infrastructure:

1. Protocol X-Ray (ZK Proofs): Every deposit, borrow, and repay operation requires an on-chain Groth16 proof verified via the bn254.pairing_check host function introduced in Stellar's ZK infrastructure upgrade. This is the first lending protocol to use this capability in production.

2. Stellar Asset Contract (SAC): The lending pool holds and distributes native Circle USDC through the standard SAC interface — not a synthetic or wrapped token. Borrowers receive the same USDC used by banks, fintechs, and remittance networks.

3. Soroban Compute: The bitcoin-spv contract performs SHA256d block header verification, Merkle proof validation, and transaction parsing entirely on-chain — operations that require Soroban's extended compute budget.

4. Anchor Ecosystem Compatibility: Because Writz outputs standard Stellar USDC, borrowers can immediately use the existing Stellar anchor network (MoneyGram Access, local off-ramps) to convert loans into local currency cash.

## Competitive Advantage

- Non-custodial BTC: WBTC and tBTC use custodians. Stacks sBTC uses a federation. Writz uses Bitcoin Script — no counterparty.
- No BTC wrapping: Competitors wrap BTC into synthetic tokens. Writz keeps real BTC on Bitcoin.
- Private positions: No other lending protocol hides positions with ZK proofs. Writz uses Groth16 for full privacy.
- Native USDC output: Writz outputs Circle's native USDC on Stellar — the same USDC used by banks and fintechs worldwide.
- Emergency exit: If Writz disappears, the CLTV timelock lets users reclaim BTC unilaterally. No other protocol offers this.
